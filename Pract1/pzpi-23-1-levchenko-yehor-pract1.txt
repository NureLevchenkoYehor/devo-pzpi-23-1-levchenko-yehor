2 ЗАВДАННЯ
     Метою роботи є формування практичних навичок командної розробки з використанням системи контролю версій Git, опанувати стратегію Trunk-Based Development, навчитися створювати гілки, виконувати злиття (merge), розв’язувати конфлікти та проводити Code Review.
     У межах роботи необхідно:
* налаштувати локальний та віддалений Git-репозиторій;
* опанувати модель Trunk-Based Development на практиці;
* створити та вирішити штучно згенерований merge-конфлікт;
* оформити Pull Request (PR) із проведенням взаємного рецензування коду;
* підготувати відеодоповідь;
* оформити звіт відповідно до ДСТУ 3008:2015.


3 ОПИС ВИКОНАНОЇ РОБОТИ
     Через веб-інтерфейс GitHub, було створено новий пустий віддалений репозиторій із назвою devops-lab1 [1] та основною гілкою main. За допомогою команди git clone, цей репозиторій було завантажено на робочу машину.
     У директорії локального репозиторію, було створено файл скрипту, написаний мовою програмування Python, із назвою main.py. Цей скрипт запитує у користувача ціле число та виконує його перевірку на простоту (див. дод. В, підрозділ В.1).
     Новий файл було додано у локальний репозиторій за допомогою команди git add. Для збереження нового стану локального репозиторію, зміна була збережена викликом команди git commit, із вказанням повідомлення “Init” через прапорець m (скорочення від message). Збережені зміни у локальному репозиторії були відправлені на віддалений репозиторій за допомогою команди git push.
     Наступним кроком, було вирішено додати логіку валідації вхідних даних користувача. Для цього, було створено нову гілку з використанням команди git checkout із флагом b (скорочення від branch) та вказанням назви гілки feature/input-validation. У сучасних версіях Git також існує альтернативний варіант із використанням команди git switch та флагом c (скорочення від create), із вказанням назви нової гілки.
     Принцип роботи із новою гілкою ідентичний до того, що було описано раніше. До файлу скрипту було додано код валідації (див. дод. В, підрозділ В.2), після чого зміни були збережені послідовним виконанням git add та git commit із повідомленням за конвенцією типу “feat: add input validation for non-integer values”. Для збереження цих змін у віддалений репозиторій, до команди git push було додано вказання origin feature/input-validation (див. рис. 1.1). Нарешті, нова гілка була застосована до основної завдяки команді git merge, об’єднавши їх стани.

Рисунок 1.1 – Завершення роботи із новою гілкою
     Завершивши роботу із гілкою feature/input-validation, було здійснено перехід на основну гілку. В основній гілці, було створено новий файл із назвою config.json. Цей файл містить єдине поле env із значенням staging, яке не використовується у коді і слугує виключно для демонстрації конфлікту. Новий файл було збережено у локальному репозиторії та відправлено на віддалений репозиторій.
     Було створено нову гілку із назвою feature/config. В цій гілці, до файлу конфігурації були внесені зміни, які змінили значення поля env на dev. Після того, як ці зміни були збережені у локальному репозиторії, було здійснено повернення на основну гілку.
     Зміни, здійснені у гілці feature/config, ще не вплинули на стан файлу конфігурації в основній гілці, тому значення env досі встановлене як staging. Змінивши це значення на production, новий стан було збережено в локальному репозиторії та відправлено у віддалений.
     На даному етапі, спроба об’єднання основної гілки та гілки feature/config призвела до конфлікту (див. рис. 1.2). Гілка feature/config базувалася на стані конфігураційного файлу до змін, внесених та збережених після її створення, через що автоматичне вирішення даного конфлікту неможливе.

Рисунок 1.2 – Конфлікт з’єднання
     У файлі, в якому виник конфлікт, було додано спеціальну розмітку, яка ділить змінені фрагменти коду на ті, що були у поточній гілці, та ті, що йдуть з гілки, яку ми намагаємося приєднати. Сучасні інструменти розробки розпізнають дану розмітку та надають відповідні підказки, разом із доступними діями (див. рис. 1.3).

Рисунок 1.3 – Вигляд конфлікту у VS Code
     Конфлікт, що виник, було усунуто шляхом вибору фрагменту коду, який повинен залишитись у коді. В даному прикладі, було вирішено залишити значення  env рівним production. Після внесення цієї зміни, її було збережено у локальному репозиторії із відповідним повідомленням про розв’язання конфлікту. Дерево репозиторію, отримане в результаті, наведено на рисунку 1.4.

Рисунок 1.4 – Дерево репозиторію
     Для демонстрації процесу рецензування коду, було створено ще одну гілку із назвою feature/optimize-prime-check. В цій гілці, попередній код було оновлено для його оптимізації (див. дод. В, підрозділ В.3). Ці зміни були збережені та надіслані на віддалений репозиторій. Проте, команда з’єднання не прописувалась.
     Попередньо, за відсутності інших студентів, які могли б виконати рецензування, до репозиторію, в якості контріб’ютора, було додано мій приватний профіль. Завдяки цьому, при створені запиту, я міг вказати свій профіль в якості рецензента, не хвилюючись про відсутність прав (див. рис. 1.4).

Рисунок 1.4 – Інтерфейс відкриття запиту GitHub
     У ролі рецензента, я міг перевіряти фрагменти коду, залишати коментарі, та надіслати свої висновки, дозволивши злиття гілок. (див. рис. 1.5) Враховуючи те, що приклад є навчальним, рецензування пройшло перевірку без жодних проблем.

Рисунок 1.5 – Інтерфейс рецензування GitHub
     Так як репозиторій не було налаштовано, фактична кількість необхідних дозволів на злиття за замовчуванням не визначена. Проте, у реальних репозиторіях, відсутність певної кількості дозволів заблокувала б можливість злиття гілок.
